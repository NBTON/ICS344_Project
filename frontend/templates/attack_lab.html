🔄 Replay Attack

A replay attack captures valid encrypted messages and resends them later. Without proper protection, the server cannot distinguish between original and replayed messages, allowing attackers to duplicate transactions or actions.

How it works:

  1. Attacker intercepts an encrypted message between Alice and Bob
  2. The message is valid and properly encrypted
  3. Attacker saves the message and resends it later
  4. Without defense: Server accepts the duplicate message
  5. With defense: Timestamp and nonce validation reject the replay

Defense Mechanism:

  • Timestamp validation: Messages must be within 5-minute window
  • Nonce tracking: Each nonce can only be used once
  • Combined protection: Both checks must pass

✏️ Ciphertext Tampering Attack

Ciphertext tampering involves modifying encrypted data in transit. Without authenticated encryption, changes may go undetected and could corrupt the decrypted message in unpredictable ways.

How it works:

  1. Attacker intercepts an encrypted message
  2. Attacker modifies bytes in the ciphertext
  3. Modified ciphertext is forwarded to recipient
  4. Without AEAD: Decryption may produce corrupted plaintext
  5. With AES-GCM: Authentication tag validation fails

Defense Mechanism:

  • AES-GCM: Authenticated Encryption with Associated Data
  • 128-bit auth tag: Cryptographic integrity check
  • Tamper detection: Any modification invalidates the tag

👤 Man-in-the-Middle Attack

In a MITM attack, an attacker positions themselves between two parties, intercepting and potentially modifying all communications. During key exchange, they can substitute their own keys to decrypt all messages.

How it works:

  1. Alice requests Bob's public key from server
  2. Attacker intercepts and returns their own key
  3. Alice encrypts messages with attacker's key
  4. Attacker decrypts, reads, re-encrypts for Bob
  5. Both parties unaware of the interception

Defense Mechanism:

  • RSA-PSS Signatures: Sign all key exchanges
  • Key fingerprints: Verify through secondary channel
  • Public key binding: Keys tied to verified identities

💥 Denial of Service Attack

A DoS attack floods the server with requests, consuming resources and preventing legitimate users from accessing the service. Without rate limiting, even a single attacker can overwhelm the system.

How it works:

  1. Attacker sends many requests per second
  2. Server processes each request consuming CPU/memory
  3. Resources exhausted, legitimate requests timeout
  4. Service becomes unavailable to real users

Defense Mechanism:

  • Token bucket algorithm: Limit requests per time window
  • Per-IP tracking: Separate limits for each client
  • Graduated limits: Different rates for different endpoints
  • HTTP 429: "Too Many Requests" response when limited
